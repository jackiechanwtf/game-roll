# Как здесь работают тесты и CI

## Что такое автотест

Это обычная Python-функция, которая выполняет действие и сравнивает результат с ожидаемым. Например, `test_health_version_and_web_page` обращается к `/health` и проверяет, что сервис отвечает `{"status": "ok"}`.

```python
assert client.get("/health").json() == {"status": "ok"}
```

`assert` означает «проверь, что условие истинно». Если вместо `ok` придёт `broken`, тест завершится ошибкой. Так можно обнаружить поломку до того, как её увидят друзья.

Тесты находятся в `test_app.py`. Их запускает библиотека `pytest`:

```bash
python -m pip install -r requirements-dev.txt
python -m pytest -v
```

Ключ `-v` показывает название и результат каждого случая: `PASSED` или `FAILED`.

## Почему не нужно вручную запускать сайт перед тестами

`TestClient` обращается к FastAPI внутри Python. Отдельный сервер, порт и браузер для этих проверок не нужны. Конструкция `with TestClient(...)` также выполняет запуск и остановку приложения, поэтому проверяются настройки и создание хранилища.

Функция `create_app(...)` позволяет передать тестовый каталог и путь к временному JSON-файлу. `pytest` создаёт для каждого теста отдельную папку через `tmp_path`. Тесты не используют `data/state.json` и не меняют историю друзей.

`@pytest.fixture` — подготовка, которую используют несколько тестов. Наша фикстура `client` создаёт приложение и заменяет случайный выбор предсказуемым. Это позволяет проверить, что повторов нет, не рассчитывая на удачу.

## Какие ситуации проверяются

| Проверка | Зачем нужна |
| --- | --- |
| `/health`, `/version`, HTML и JavaScript | Сервис и основные файлы интерфейса доступны |
| Ограничение длительности и неверные параметры | В подборку не попадает слишком длинная игра, ошибки ввода обрабатываются |
| Пустые имена и повторный вход | Не появляются пустые игроки и дубликаты имён из-за регистра |
| Принятие первой игры | Игра появляется в таблице и блокирует следующий розыгрыш |
| Третья попытка и запрет четвёртой | Правило двух перебросов выполняется на сервере |
| Действие из старой вкладки | Старый запрос не расходует ещё одну попытку и не принимает невиденную игру |
| Завершение игры с часами и комментарием | Статус, потраченное время и текст сохраняются, затем можно выбирать следующую игру |
| Неверное время и повторное сохранение | Отрицательные и некорректные часы отклоняются, а готовый результат нельзя случайно перезаписать |
| Личные повторы и разные игроки | Уже выпавшая игроку игра исключается, но может выпасть его другу |
| Перезапуск сервера | Попытки, принятые игры, потраченные часы и комментарии остаются в файле |
| Два одновременных запроса | Для одного игрока не создаются два параллельных розыгрыша |
| Переменные окружения и логи | Список игр загружается из `GAMES_FILE`, история сохраняется по `GAME_ROLL_DATA`, события попадают в логи |
| Повреждённый файл истории | Ошибка чтения не стирает сохранённую историю |

Некоторые функции запускаются с несколькими наборами данных через `@pytest.mark.parametrize`. Например, завершение проверяется отдельно для `completed` и `dropped`. Поэтому число строк `PASSED` больше числа функций.

Эти тесты проверяют API и правила сервиса. Внешний вид и действия через настоящий браузер проверяются отдельно вручную.

## Что такое CI

CI — автоматическая проверка изменений в репозитории. Здесь её выполняет **GitHub Actions** по инструкции `.github/workflows/ci.yml`.

После `git push` GitHub выделяет временный компьютер с Linux и последовательно:

1. Скачивает код через `actions/checkout`.
2. Устанавливает Python 3.12 через `actions/setup-python`.
3. Устанавливает зависимости из `requirements-dev.txt`.
4. Выполняет ту же команду, что и локально: `python -m pytest -v`.
5. При успешных тестах сохраняет файлы приложения в artifact `game-roll`.

Проверка запускается на `push`, на `pull_request` и вручную кнопкой **Run workflow**. Настройка `permissions: contents: read` даёт workflow право читать код; записывать изменения в репозиторий ему не нужно.

Если тест не проходит, шаг завершается с ненулевым кодом, запуск помечается красным и artifact не создаётся. Исправление и следующий `push` запускают проверку снова.

## Что такое artifact

Это ZIP с файлами, который GitHub сохраняет рядом с результатом успешной проверки. Его можно скачать внизу страницы запуска, в разделе **Artifacts → game-roll**.

Внутри находятся Python-код, каталог игр, интерфейс, тесты, зависимости и инструкции. Можно распаковать архив в отдельную папку и запустить проект по README. Личная история `data/state.json`, настоящее `.env` и виртуальное окружение туда не включаются.

Artifact подтверждает, какие файлы сохранены после успешной проверки. Сам сайт CI не размещает: для работающего общего сайта нужен отдельно запущенный FastAPI-сервис.

## Где смотреть ошибки

Открой репозиторий → **Actions → Tests → нужный запуск → test → Run tests**. В логе будут название упавшего теста, запрос и сравнение ожидаемого результата с фактическим.

Для локальной проверки одного сценария:

```bash
python -m pytest -v -k third_game
```

Если ошибка возникает только в CI, проверь, что нужный файл закоммичен, зависимости указаны в requirements и путь не зависит от твоего компьютера.
